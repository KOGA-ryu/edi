# The Art Forge — procedural sacred-geometry → seamless texture → real Blender material

Status: ARCHITECTURE / pre-C0 brief (researcher, 2026-06-19). This decides the
technique for the ART FORGE: turning edi's sacred-geometry / girih patterns into
REAL, tileable, SEAMLESS textures applied as real Blender materials on zoo
assets. It is a doc only — no code is written by this brief. It rides the proven
loop: the texture becomes an `AssetRecord.textureRefs` entry consumed by the
realizer's per-slot materials (the tree craftsman already assigns bark/leaf
slots — we wire real maps into them).

The order, restated: **procedural pattern → texture ONLY** (not a freehand paint
surface — that is shelved UI). **Depth-first:** one pattern → one seamless
texture → one real material on one asset → render. Parametric + reproducible
(named pattern params, no hardcoded dims), headless / gateable.

---

## 0. The decision, up front

**The rasterizer fork is (b): a Blender-side ORTHOGRAPHIC BAKE of a
pure-Python periodic-tiling generator.** No new C++. No drafting sub-campaign is
flagged. The sacred-geometry MATH is what is reused — regenerated in Python as a
new craftsman-shaped generator, exactly the way `nfold_star.py` regenerates the
girih star math the C++ core never owned.

One-line bridge for `textureRefs`: a textureRef gains a second shape — a
**catalog-relative image path** (`textures/girih_floor.png`, resolved against
`--asset-dir` like `meshRef`) — and `_instance_material` loads it as an
Image-Texture map into the slot, **keeping the flat-color name path as the
fallback** (greybox + existing assets untouched).

The chosen first motif: an **8-pointed star-and-cross**, wallpaper group **p4m
(\*442)**, square translational unit cell, generated by `n=8 / k=3` girih-star
math + a complementary cross — periodic by construction.

## 1. The rasterizer fork — why (b) wins and (a) loses

The question: how does 2D sacred-geometry pattern geometry become a seamless
PNG? Two candidates.

### (a) Drafting-side C++ → SVG → rasterize → PNG — REJECTED

To do this we would need BOTH:

  (i) a **NEW girih-TILING authoring** inside the C++ drafting core. GROUNDED
      FACT: none exists. `src/drafting/DraftingSvgOut.{h,cpp}` (`svgFromPlotJob`,
      pure / no-Qt) only renders a **plot job's pen strokes** to SVG — it is a
      stroke serializer, not a sacred-geometry pattern source. The drafting core
      has no wallpaper-group / lattice / star-tiling generator to reuse. So (a)
      is not "reuse the kit"; it is "write a tiling kit that does not exist yet."

  (ii) a **NEW SVG → PNG rasterizer**. `QSvgRenderer` is Qt — and the core is on
      a deliberate de-Qt direction (the drafting core is Qt-free; `svgFromPlotJob`
      is pure on purpose). Pulling Qt's SVG/raster modules back into the geometry
      path fights that direction; the alternative is vendoring a rasterizer
      (NanoSVG/stb, or a hand-rolled scanline fill), i.e. a third-party C++
      dependency to evaluate, license, and maintain for a job Blender already does.

That is **two new C++ pieces** (a tiling authoring layer + a rasterizer) plus a
dependency decision — a genuine **drafting sub-campaign**. It buys nothing the
forge needs that (b) does not already provide, and it lands the texture pipeline
in the wrong department (drafting, not the lab).

> NOTE / FLAG: (a) is NOT recommended. IF a future requirement forces it (e.g.
> the textures must be authored as editable drafting documents and round-trip
> through `.edidraw`), the flagged drafting sub-campaign would build exactly:
> (1) a girih/wallpaper TILING generator in `src/drafting/` as free functions
> over plain structs (a `DraftingTilingOps`-style slice, lattice + motif params
> in, plot-job strokes out), and (2) a no-Qt SVG→PNG rasterizer (vendored
> NanoSVG-class, or a scanline polygon fill emitting a PPM/PNG). The hub should
> route THAT to edi-drafting, not the lab. This brief does not request it.

### (b) Blender-side ortho bake of a pure-Python tiling generator — CHOSEN

Generate the periodic tiling as flat 2D geometry (filled polygons / a colored
mesh) on a plane in `bpy`, render with an **orthographic top-down camera framed
to exactly ONE repeat unit** (or N×N), output a PNG. The pattern geometry is
PURE PYTHON — a new periodic-tiling generator that reuses the sacred-geometry /
girih math the existing craftsmen already embody (`nfold_star.py`'s `{n/k}`
star, `radial_petal.py`).

Scored against the brief's gates:

| Gate | (a) C++→SVG→PNG | (b) Blender ortho bake |
|---|---|---|
| Reproducible | yes, but needs a deterministic rasterizer | yes — pure-Python motif is a closed-form function of params (the `nfold_star` discipline); the bake is a fixed ortho framing |
| Headless / gateable | rasterizer runs headless, but the PIXELS need a full new toolchain to verify | **the MOTIF GEOMETRY proof runs with NO Blender** (a pure `tile_polys(params)` tier, exactly like `proof_mesh`); only the final PNG needs Blender, same as every other craftsman |
| No new C++ | NO — two new C++ pieces + a dep | **YES — zero new C++** |
| Parametric dial-ability | yes | **yes — a `MANIFEST` of named number/integer/material params, no hardcoded dims** |
| Seamlessness control | manual — must compute the SVG viewBox to the cell | **structural — the ortho camera `size` = the cell width frames exactly the lattice cell; opposite edges match by the periodicity of the construction (§3)** |

(b) reuses the proven dual-tier shape (`MANIFEST` + pure generator + `bpy`
twin), reuses the proven loop (`textureRefs` → realizer slots), needs zero new
C++, and makes seamlessness a property of the framing rather than a hand-tuned
viewBox. It is the clear fit.

**Addressing the "reuse the drafting kit" intent:** the C++ kit has nothing to
reuse for TILINGS (verified: `DraftingSvgOut` is a stroke serializer, no lattice
math). What is genuinely reused is the sacred-geometry MATH — the `{n/k}`
compass construction — and it is reused the way the lab already reuses it: as a
pure Python generator, the `nfold_star` pattern. So (b) honors the intent
("reuse our sacred geometry") without the fiction that a tiling generator exists
in C++ to call.

## 2. The pattern generator — design

### 2.1 The motif, its group, its fundamental domain

**Motif:** the classic Islamic **8-pointed star-and-cross** ("khatam" /
star-and-cross tessellation). An 8-point star sits at each square-lattice node;
the leftover space between four stars forms a cross (a concave octagon /
elongated cross). Stars + crosses tile the plane with no gaps.

**Wallpaper group: p4m** (orbifold \*442) — the most common group for Islamic
geometric design, alongside p6m (\*632) [Rønning; Bridges 2014]. p4m sits on a
**square lattice** and adds 4-fold rotation centers at the lattice nodes plus
mirror lines through them.

**Two different "units" — do not conflate them (load-bearing):**

  * The **generating fundamental domain** of p4m is a **right triangle, 1/8 of
    the square** (one octant) — the minimal patch the symmetry operations
    (4 rotations × 2 mirrors) replicate to fill the cell. This is what
    mathematicians mean by "fundamental domain." [Bridges 2014; Taalman & Yackel,
    Bridges 2020]

  * The **translational unit cell** is the **whole SQUARE** — the patch that
    tiles by pure TRANSLATION (the lattice vectors), with no rotation or
    reflection needed.

> **FRAME THE SQUARE, not the triangle.** Seamless image tiling repeats a
> texture by pure translation (Blender "Repeat" extension / a 3×3 lay-up). The
> patch that tiles by translation is the SQUARE translational cell. The triangle
> only tiles if you also reflect/rotate it, which an image-repeat node cannot do.
> So the generator produces — and the camera frames — the full square cell. The
> p4m symmetry is still what we EXPLOIT to BUILD that square cheaply (build one
> octant, mirror/rotate it into the square), but the rendered tile is the square.

For C0 simplicity we may start with the even-simpler **p4** square cell (the
star-and-cross laid out by 4-fold rotation only, no mirror) and promote to full
p4m once the bake is proven; both share the square translational cell, so the
framing and seam check are identical. The motif above is p4m by construction
(the star is itself mirror-symmetric), so this is a free upgrade.

### 2.2 Parametric construction (reproducible, no hardcoded dims)

The cell is a unit square `[0,cell] × [0,cell]`. All geometry is a closed-form
function of the params — the `nfold_star` discipline: "a TOOL the author dials,
not a generator; every vertex is a closed-form function of the params, nothing
random or auto-laid-out."

Construction (per cell, origin at cell min-corner):

  1. **Star at each corner-shared node.** Place an `{8/k}` star (the
     `nfold_star` `{n/k}` math, with `n=8`) centered at the cell's 4-fold center.
     With p4m the star center sits at the cell center; copies at the cell corners
     are supplied by the neighbors' translation (this is WHY the edges match).
  2. **Star outline** = the 16-vertex alternating tip/valley ring of
     `nfold_star._local_mesh` (tips at radius `starRadius`, valleys at the
     `{8/k}`-derived inner radius). Reused math, regenerated in Python.
  3. **Cross / interstitial fill.** The region between four stars is the
     cross/octagon; it is the cell minus the star sectors, filled as the
     background polygon. Its color is the "ground" of the pattern.
  4. **Line vs fill.** Each region (star, cross, ground) is a FILLED colored
     polygon (so the texture has real colors, not line art — see Risks §6). An
     optional stroke outline of width `lineWidth` (in cell-fraction) is laid on
     the region boundaries for the "drawn" girih look.

### 2.3 The MANIFEST-style param set (named, no hardcoded dims)

Mirrors a craftsman `MANIFEST` (only number/integer/material/string-ish types a
flat param bag carries). Proposed for the tiling craftsman (`girih_tile`):

| key | label | type | default | role |
|---|---|---|---|---|
| `points` | Star Points (n) | integer | 8 | the `{n/k}` star order (8 = octagram) |
| `skip` | Star Skip (k) | integer | 3 | `{n/k}` sharpness; reuses `nfold_star._resolve_k` coprime guard |
| `cell` | Cell Size | number | 1.0 | the translational unit-cell edge (Blender units); the ortho camera spans exactly this |
| `starRadius` | Star Radius (frac) | number | 0.42 | star tip radius as a fraction of `cell` — kept < 0.5 so a corner star and its translated neighbor meet without overlap |
| `lineWidth` | Line Width (frac) | number | 0.02 | outline stroke width as a fraction of `cell` (drives READS-AT-SCALE; see rubric) |
| `pxPerCell` | Pixels / Cell | integer | 1024 | render resolution of ONE cell (the PNG is `pxPerCell` square, or `N*pxPerCell` for an N×N bake) |
| `repeat` | Bake Repeats (N) | integer | 1 | render an N×N lay-up into the PNG (1 = a single repeat unit; N>1 bakes a pre-tiled sheet) |
| `starColor` | Star Color | material | gold | star region fill |
| `crossColor` | Cross Color | material | azure | cross/interstitial fill |
| `groundColor` | Ground Color | material | indigo | background fill |
| `lineColor` | Line Color | material | black | outline stroke |

No dimension is a magic literal in the build logic — every length is a
`cell`-relative fraction (the realizer's "no hardcoded dimensions" invariant, and
the `nfold_star` "every vertex is a function of the params" rule). `cell` is the
single scale knob; `pxPerCell` is the single resolution knob.

### 2.4 Dual-tier shape (the proven craftsman contract)

Same three-part contract as every craftsman, so the geometry is gateable WITHOUT
Blender:

  * `MANIFEST` — id `girih_tile`, the params above.
  * `tile_polys(params) -> [(polygon_2d, color_key)]` — **PURE, no bpy.** The
    deterministic motif: the list of filled colored polygons that compose ONE
    cell (the `proof_mesh` analog). This is what the offline rubric tests assert
    (symmetry, vertex counts, edge-wraparound). It is also what an OBJ/SVG-ish
    proof tier could dump for eyeballing.
  * `build(op)` / a bake entry — the `bpy` twin: lay the polygons as flat filled
    faces (or a mesh with per-face materials) on the Z=0 plane, set up the ortho
    camera + the PNG output, render. Calls `tile_polys` — ONE generator, no
    second copy of the math (the `nfold_star`/`tree` parity rule).

This forge generator lives in the Python forge layer (a new
`tools/blender/craftsmen/girih_tile.py` or a dedicated `tools/blender/forge/`
module). Cores stay isolated; no C++; additive.

## 3. Seamlessness — the framing rule and the check

### 3.1 Why framing the translational cell gives matching edges

A wallpaper pattern is **invariant under its lattice translation vectors** — for
the square lattice, translation by `cell` in X or Y maps the pattern exactly onto
itself [p4 / square-lattice tiling; ResearchGate unit-lattices]. Therefore the
strip of pattern at `x = 0` is, pixel for pixel, the strip at `x = cell`; same
for `y`. If the ortho camera frames the rectangle `[0,cell] × [0,cell]` exactly,
the **left edge column equals the right edge column** and the **bottom row equals
the top row** — the texture is seamless by construction, not by retouching. This
is the structural advantage over hand-painted seamless textures.

The motif must be authored so that whatever crosses an edge re-enters on the
opposite edge: place the star centers at the lattice nodes (cell center +
corners) so each edge carries exactly one half-star that completes against its
translated neighbor. (This is the construction in §2.2 — the corner stars come
from neighbor translation.)

### 3.2 The ortho-camera framing math (pixel-aligned)

From the Blender ortho-tile recipe [GameFromScratch; Urho3D wiki]:

  * Camera: ORTHOGRAPHIC, looking straight down −Z, at `(cx, cy, +h)` where
    `(cx, cy)` is the cell center and `h` any positive height (ortho ignores
    distance for scale).
  * **`camera.data.ortho_scale = cell * repeat`** — the ortho frustum spans
    exactly `cell` Blender units across its LONGER dimension. For a square render
    (`res_x == res_y`) the framed square is exactly the cell (× `repeat`).
  * **`render.resolution_x = render.resolution_y = pxPerCell * repeat`**, square.
    Pixel-aligned: each cell is exactly `pxPerCell` pixels, so an integer N×N bake
    has no fractional-pixel drift at the internal seams.
  * No perspective ⇒ no foreshortening ⇒ the cell maps linearly to the image,
    so the periodic equality of §3.1 survives into pixel space.
  * Render film: transparent OFF (we want the ground color, not alpha), color
    management set so the flat fills are not tone-mapped away from their authored
    values (use a Standard / Raw view transform for the bake so `starColor` etc.
    land as authored — see Risks §6 on color).

### 3.3 The concrete seam check (the gate's verification)

Two tiers, mirroring the dual-tier discipline:

  * **OFFLINE (no render, no Blender) — the primary gate.** From the baked PNG
    via PIL/Pillow: read pixel column `x=0` and column `x=W-1`; they must be
    equal within ε (ε accounts for anti-aliasing on the boundary). Same for row
    `y=0` vs row `y=H-1`. This is a pure-pixel assertion, runs in CI, no GPU.
    Computable: `max |left - right| <= EPS` and `max |top - bottom| <= EPS`.
  * **VISUAL (render) — confirmation.** Lay the PNG up 3×3 (PIL paste, or Blender
    Image-Texture with the **Repeat** extension on a quad) and inspect: no visible
    seam line, no doubled/missing motif at the joins, the star straddling a join
    completes into one star. The reviewer eyeballs a snapshot once (the lab's
    "eyeball offscreen" habit).

The OFFLINE check is the load-bearing one — it makes seamlessness a computable
gate, not an opinion.

## 4. The bpy material pipeline — PNG → real material

### 4.1 The minimal node graph (base color)

The smallest real material (the C2 target):

```
Image Texture (the baked PNG)  ──Color──▶  Principled BSDF · Base Color
   - .image = loaded girih PNG
   - .extension = 'REPEAT'        # tile across the UV — this is where seamlessness pays off
   - .interpolation = 'Linear'    # (or 'Closest' for crisp pixel edges; see rubric CRISPNESS)
UV Map / Texture Coordinate (UV) ──Vector──▶ Image Texture · Vector
```

The asset's UVs decide tiling DENSITY: scaling the UVs (a Mapping node `Scale`,
or the mesh UV layout) makes the texture repeat M times across a 5 ft wall — a
named, dial-able density (rubric: "M repeats across a 5 ft wall").

### 4.2 Optional relief — normal + roughness ("depth", C4)

"The Blender profile gives the figures depth." Two routes to derive a relief map
from the SAME pattern, both pure-Python from the polygons or pixel-derived from
the PNG:

  * **HEIGHT from line proximity.** Author a grayscale HEIGHT map where pixels ON
    a region boundary (the girih lines) are dark (recessed groove) or light
    (raised bevel) and interiors are mid-gray, as a function of distance to the
    nearest boundary. The generator already knows every polygon edge, so a signed
    distance to the nearest edge → height is a closed-form per-pixel value (or a
    cheap distance transform on the line mask via PIL). Wire: Image Texture
    (height) → Bump node → Principled BSDF · Normal. (Bump from a height map needs
    no tangent-space normal encoding — simplest first relief.)
  * **NORMAL map** (later): convert the height map to a tangent-space normal via
    a Sobel gradient (PIL/numpy) → Image Texture (Non-Color) → Normal Map node →
    Principled · Normal. More correct than Bump, more machinery.
  * **ROUGHNESS** from the region mask: e.g. the gold star slightly glossier than
    the indigo ground → a per-region grayscale roughness PNG → Image Texture
    (Non-Color) → Principled · Roughness.

All three are EXTRA baked PNGs from the same generator (one per channel). Each is
an additional `textureRefs` entry; the material wires whichever are present and
defaults the rest. C4 gate is depth READS in the render.

### 4.3 Apply at REALIZE time vs baked into the asset .blend

Two valid points to attach, both already modeled by the realizer:

  * **REALIZE-time override (recommended for C0–C3).** The placement carries the
    texture refs; `_instance_material` builds the Image-Texture material as an
    **OBJECT-level slot override** — exactly the mechanism the tree's
    `bark_brown`/`leaf_green` flat colors use today (per-slot, in order, on the
    Object not the shared mesh). This keeps build-once instancing intact (the
    shared mesh datablock is never mutated) and lets the same mesh wear different
    textures per placement. The PNG is loaded once and cached (sibling to the
    `mesh_cache` / `baked_cache` pattern).
  * **Baked into the asset .blend** (later, for curated hero assets): the
    craftsman's `build` assigns the Image-Texture material to the slot at
    bake-time and packs/points the PNG, so the linked mesh "arrives WITH a baked
    material" — the existing `had_baked` path then SHARES it (no override). This
    is the path for an asset whose texture is intrinsic.

For the depth-first C-ladder, do REALIZE-time override first (smallest change,
reuses the proven slot-override path); promote to baked-in only when a hero asset
wants its texture intrinsic.

## 5. The textureRefs evolution — the C2/C3 bridge

### 5.1 Today (verified)

`AssetRecord.textureRefs` (`src/zoo/AssetZoo.h`) is a `std::vector<std::string>`
of free-form refs. In the TOON manifest they ride as a `·`-joined run
(`ZooToonExport`), parsed back into `Asset.textures` (`edi_realize.py`). At
render they are mapped by NAME to FLAT COLORS in `GREY_MATERIALS`
(`bark_brown`, `leaf_green`, `instance`, …) and assigned per-slot in order by
`_instance_material`. They are appearance-only, additive, touch no core.

### 5.2 Proposed — a textureRef MAY be an image-file path

Give a textureRef a second, BACKWARD-COMPATIBLE shape, distinguished by syntax
(no schema change, no version bump — the additive discipline):

  * **A bare name** (`bark_brown`, `leaf_green`) → unchanged: a `GREY_MATERIALS`
    flat-color key. This is the FALLBACK and keeps greybox + every existing asset
    byte-identical.
  * **A catalog-relative image path** — recognized by a `/` and an image
    extension, or a `tex:` prefix to be explicit — e.g. `textures/girih_floor.png`.
    Resolved against `--asset-dir` EXACTLY like `meshRef`
    (`os.path.join(asset_dir, ref)`), the same catalog-relative-POSIX-key
    discipline (`Asset.meshRef` docs). The PNG lives in the asset catalog
    alongside the `.blend` meshes (a `textures/` subdir), NOT on the TOON wire
    (the wire carries the opaque ref; the bytes live in the catalog) — matching
    "the catalog is index, not geometry."

### 5.3 The `_instance_material` extension (flat-color fallback PRESERVED)

`_instance_material` gains a per-name branch (keeping every existing path):

  * If the ref resolves to an existing image file under `--asset-dir`: build a
    material whose Principled Base Color is driven by an **Image Texture** node
    loaded from that PNG (the §4.1 graph), `extension='REPEAT'`. Optionally, if
    sibling `_normal` / `_rough` PNGs are present (or additional refs name them),
    wire those channels (§4.2).
  * Else (a bare name, or the file is missing): the CURRENT path — `_bpy_material`
    flat color, falling through to `stone`. So a missing texture degrades to a
    legible flat color, never crashes (mirrors the missing-`.blend`
    "warn-and-skip" robustness).

The PNG is loaded once per path and cached (a `bpy.data.images` lookup or a small
dict), sibling to the mesh/baked caches, so N placements sharing a texture link
ONE image datablock.

**Boundary (the law this respects):** texture generation + the bake live in the
forge / Python layer; the produced PNG is an `AssetRecord.textureRefs` entry; the
cores stay isolated; no JSON; everything additive. The C++ side learns nothing
new — `textureRefs` is already an open-vocabulary string list; an image path is
just another string it records without interpreting (the neutral-vocab law from
`AssetZoo.h`).

## 6. Enriched critique rubric — concrete, checkable tests

The brief's six dimensions, sharpened into tests with a stated method and whether
each is computable OFFLINE (from the PNG via PIL/numpy, no GPU) or needs a RENDER.
Priority order is the brief's: **SEAMLESS > FIDELITY > CRISPNESS > READS-AT-SCALE
> REPRODUCIBLE > PIPELINE-FIT.**

| # | Dimension | Concrete test | Method | Offline? |
|---|---|---|---|---|
| 1 | **SEAMLESS** (top gate) | `max|col(x=0) − col(x=W−1)| ≤ ε` AND `max|row(y=0) − row(y=H−1)| ≤ ε` (ε ≈ a few/255 for AA) | PIL: read edge rows/cols, compare arrays | **OFFLINE** |
| 1b | SEAMLESS (visual) | 3×3 lay-up shows no seam line, no doubled/clipped motif; a star on a join completes | PIL paste 3×3, eyeball; or Blender Repeat quad | render/eyeball |
| 2 | **FIDELITY** (symmetry) | the motif has the claimed group: the cell is invariant under 90° rotation about its center (p4) and under the mirror axes (p4m) | PIL: rotate the array 90° / flip, compare to original within ε; OR assert on `tile_polys` vertex set | **OFFLINE** |
| 2b | FIDELITY (counts) | the star has exactly `2*points` boundary vertices; `{n/k}` coprime guard honored (no degenerate star) | assert on `tile_polys` output | **OFFLINE** |
| 3 | **CRISPNESS** | line/edge AA does not blur the figures into mush: along a known boundary, the 10–90% color transition spans ≤ T pixels | PIL: sample a scanline across a star tip edge, measure transition width | **OFFLINE** |
| 4 | **READS-AT-SCALE** (line width) | `lineWidth` renders ≥ N px at `pxPerCell=1024` (e.g. N≥3) so lines survive mip/minification | PIL: measure the thinnest dark stroke run; OR compute `lineWidth*pxPerCell` | **OFFLINE** |
| 4b | READS-AT-SCALE (density) | the texture tiles M repeats across a 5 ft wall and the motif is still legible at that density | render the textured wall, count repeats / eyeball | render |
| 5 | **REPRODUCIBLE** | same params ⇒ byte-identical `tile_polys` AND byte-identical PNG across reruns; no hidden RNG (the motif is closed-form) | run twice, `diff` the polygons and the PNG bytes | **OFFLINE** |
| 6 | **PIPELINE-FIT** | the PNG resolves as a `textureRefs` image path under `--asset-dir`; `_instance_material` loads it; a bare name still falls back to flat color; greybox render byte-identical | the realizer smoke / OBJ proof + one render | mostly OFFLINE (resolution + fallback in the pure tier), final in render |

Most gates are OFFLINE — seamlessness, symmetry, crispness, line width,
reproducibility, and the textureRef resolution all reduce to PNG-pixel or
`tile_polys`-polygon assertions runnable in CI with no GPU. Only the visual
seam confirmation, the at-scale density read, and the final material render need
Blender. This is the same "pure tier the reviewer/CI asserts; bpy is the final
effector" split the realizer and craftsmen already live by.

## 8. Risks / open questions

  * **Seam at the fundamental-domain boundary.** The #1 risk. Mitigation:
    author star centers AT lattice nodes so each edge carries a half-star that
    completes against the translated neighbor; FRAME the square translational cell
    (not the p4m triangle); gate on the offline edge-match test (§3.3). If the
    edge-match fails, the motif placement is wrong, not the framing — re-derive
    the corner-star contribution.

  * **Anti-aliasing vs crispness.** AA softens the edge columns the seam test
    reads (so ε must allow a few levels) AND blurs thin girih lines
    (READS-AT-SCALE). Tension: too much AA → mushy lines + a fuzzier seam; too
    little → jaggies. Open question: render at high samples then the edges are
    AA'd consistently on both sides (so the seam still matches), OR render with
    `interpolation='Closest'` / 1 sample for pixel-crisp lines. Likely: bake
    crisp (high res, modest AA), let the MATERIAL's Linear interpolation soften at
    use. Decide empirically at C1/C4.

  * **Normal-map derivation.** Bump-from-height (line proximity) is the cheap
    first relief; a true tangent-space normal map (Sobel of the height) is more
    correct but more machinery. Open: is line-proximity height enough for the
    "figures have depth" read, or do the star facets need authored bevels? Defer
    to C4; start with Bump.

  * **Texture-file packaging: in the .blend vs external.** REALIZE-time override
    loads an EXTERNAL PNG from `--asset-dir` (catalog-relative, like `meshRef`) —
    simplest, keeps the catalog the single source. A baked-into-.blend hero asset
    would PACK the PNG (`bpy.ops.file.pack_all`) so the linked asset is
    self-contained. Open: which curated assets pack vs reference. Default:
    external/catalog-relative for C0–C3.

  * **COLOR — the pattern needs real colors, not just line art.** The forbidden
    read is a black-on-white line drawing. The motif must fill regions with real
    colors (`starColor`/`crossColor`/`groundColor`) — gold/azure/indigo is the
    canonical girih palette. These are `material`-type params (appearance, exempt
    from no-hardcoded-dims, like the realizer's `GREY_MATERIALS`). Open: a small
    named PALETTE in the forge layer (the `GREY_MATERIALS` pattern) vs RGB
    params. Color management for the bake must NOT tone-map the flat fills away
    from authored RGB (use Standard/Raw view transform for the bake render).

  * **Where the generator file lives.** A new `tools/blender/craftsmen/
    girih_tile.py` (scanned like the others) vs a dedicated `tools/blender/forge/`
    module. A craftsman makes it dial-able from the recipe lab UI for free; a
    forge module keeps "texture bake" conceptually distinct from "mesh build."
    Recommend: craftsman-shaped file (reuse the load/proof discipline), in a forge
    location. A planner call.
